Where you are

You have three working standalone clients (Part 1) and a gateway that can parse HTTP requests and write HTTP responses (Part 2). The remaining work is:

  1. Move the standalone client logic into the gateway's currentWindow(), lookupTier(), and increment() methods.
  2. Implement serve() to orchestrate the full request flow: routing, backend calls, the rate-limit decision, and the fLLM call.

If you tested each piece in isolation as the earlier parts suggested, this should feel like assembly rather than invention.

Transplanting your clients

Your standalone clients were complete programs with main(), System.out.println(), and their own socket management. The gateway methods have a narrower contract: take the inputs, do the network call, return the result, and throw IOException on failure. No printing. No main().

For each method:

  • Keep the socket open/send/receive/close logic.
  • Replace println() calls with a return statement.
  • Let exceptions propagate — serve() will catch them and return 502.
  • Use try-with-resources for the socket so it closes on every path.
  • Set a 3-second socket timeout, as the spec requires.

currentWindow()

This is a near-direct copy of your TimeClient. The method takes no arguments and returns a long: the window number. 

private static long currentWindow() throws IOException

Your standalone client already does:

  1. Connect to 127.0.0.1:21037
  2. Read exactly 4 bytes
  3. Decode as unsigned big-endian
  4. Divide by SECONDS_PER_WINDOW

Copy that logic in. Return the window number. If fewer than 4 bytes arrive, throw an IOException. The constants BACKEND_HOST, TIME_PORT, and SECONDS_PER_WINDOW are already defined in the gateway.

Checkpoint: temporarily add a main method or a test call in serve() that calls currentWindow() and prints the result. Confirm it matches what your standalone TimeClient produces.

lookupTier()

private static Tier lookupTier(String userId) throws IOException

Adapt your WhoisClient. The method takes a user ID and returns a Tier enum value (Tier.DEFAULT or Tier.REGISTERED).

The differences from your standalone client:

  • The user ID comes from the parameter, not hardcoded.
  • Return a Tier value, not a string.
  • A "No such domain" response maps to Tier.DEFAULT — this is not an error.
  • A record with no Tier: field or an unrecognized tier value is malformed — throw an IOException.
  • Enforce the 8,192-byte response limit.

Case sensitivity: the spec says to match the Tier: field name and the tier value case-insensitively. A record containing tier: registered is valid and maps to Tier.REGISTERED. Use equalsIgnoreCase() or convert to uppercase before comparing.

Checkpoint: test with "alice" (should return REGISTERED), "nobody" (should return DEFAULT), and "registered-test" (check the registry file to know what to expect).

increment()

private static long increment(String key) throws IOException

Adapt your RedisClient. The method takes a key string and returns the new counter value as a long.

The key will look like usage:66000123:alice — you build it in serve(), not here. This method just sends the INCR command for whatever key it receives.

Reminder of the RESP encoding: 

*2\r\n$4\r\nINCR\r\n$<key-byte-length>\r\n<key>\r\n

For reading the reply, the gateway already provides readBackendLine(). Use it instead of writing your own line reader: 

String reply = readBackendLine(socket.getInputStream());
if (!reply.startsWith(":")) {
    throw new IOException("Unexpected Redis reply: " + reply);
}
return Long.parseLong(reply.substring(1));

Wrap the Long.parseLong() in a try-catch for NumberFormatException and convert it to an IOException if it fails.

Checkpoint: call increment("test:manual") three times and confirm you get 1, 2, 3. If you restart the services, the counter resets.

The serve method

serve() is where everything comes together. Look at what the scaffold already provides: 

private static void serve(Socket client, ExecutorService backends, FakeLLMClient fllm) {
    try {
        client.setSoTimeout(5_000);
        IncomingRequest request = readRequest(client.getInputStream());

        // Your code goes here.

    } catch (RequestException exception) {
        writeSafely(client, 400, "Bad Request", exception.getMessage() + "\n");
    } catch (Exception exception) {
        System.err.println("Gateway request failed: " + exception.getMessage());
        writeSafely(client, 502, "Bad Gateway", "A backend service failed.\n");
    } finally {
        try { client.close(); } catch (IOException ignored) { }
    }
}

The scaffold handles:

  • Setting the client socket timeout.
  • Calling readRequest() (your Part 2 work).
  • Catching RequestException and returning 400.
  • Catching any other exception and returning 502.
  • Closing the client socket in finally.

Your code fills the middle. It runs in order: routing, time, key construction, concurrent fan-out, decision, and response.

Step 1: Routing

Before contacting any backend, check the method and path. This goes immediately after readRequest(): 

if (!request.path().equals("/chat")) {
    writeResponse(client.getOutputStream(), 404, "Not Found", "Not found.\n");
    return;
}
if (!request.method().equals("POST")) {
    writeResponse(client.getOutputStream(), 405, "Method Not Allowed",
        "Use POST for /chat.\n", Map.of("Allow", "POST"));
    return;
}

Order matters: check the path first, then the method. A GET /other is a 404 (wrong path), not a 405 (wrong method on the right path).

Step 2: Time and key construction

Get the current window and build the Redis key: 

String userId = request.headers().get("x-user-id");
long window = currentWindow();
String key = "usage:" + window + ":" + userId;

Time must complete before you can submit the Redis call because the window number is part of the key.

Step 3: Concurrent WHOIS and Redis

WHOIS and Redis do not depend on each other. The spec requires them to run concurrently. Use the backends executor to submit both tasks before waiting for either result: 

var tierFuture = backends.submit(() -> lookupTier(userId));
var attemptFuture = backends.submit(() -> increment(key));

Both tasks are now running on virtual threads. Now wait for the results: 

Tier tier;
long attempt;
try {
    tier = tierFuture.get();
    attempt = attemptFuture.get();
} catch (ExecutionException e) {
    tierFuture.cancel(true);
    attemptFuture.cancel(true);
    throw new IOException("Backend call failed", e.getCause());
} catch (InterruptedException e) {
    tierFuture.cancel(true);
    attemptFuture.cancel(true);
    Thread.currentThread().interrupt();
    throw new IOException("Backend call interrupted", e);
}

Submit both before waiting. If you write tierFuture.get() before submitting the Redis task, the calls are sequential, not concurrent. The whole point of using Future objects is to start both operations and then collect the results.

Why cancel both? If the WHOIS call fails, the Redis call may still be running. Cancelling it avoids wasting resources on a result you will never use. The same applies in reverse. Cancellation is best-effort — the Redis INCR may have already completed — but that is fine. The spec says no rollback is required.

Why restore the interrupt status?

When Future.get() throws InterruptedException, Java has already cleared the current thread's interrupt flag. Calling Thread.currentThread().interrupt() sets it again so that code higher in the call stack — such as the virtual thread executor — can detect that this thread was interrupted. Swallowing interrupts silently is a common concurrency bug.

Step 4: The rate-limit decision

Compare the attempt number (from Redis) against the limit for the tier (from WHOIS): 

long limit = (tier == Tier.REGISTERED) ? REGISTERED_LIMIT : DEFAULT_LIMIT;
if (attempt > limit) {
    writeResponse(client.getOutputStream(), 429, "Too Many Requests",
        "Rate limit exceeded for " + userId + ".\n");
    return;
}

The constants DEFAULT_LIMIT (3) and REGISTERED_LIMIT (10) are already defined in the gateway. The INCR return value is the attempt number: 1 for the first request, 2 for the second, and so on. When it exceeds the limit, deny.

Step 5: Call the fLLM and respond

If the request is allowed, forward the query to the fLLM and return its response: 

String query = new String(request.body(), StandardCharsets.UTF_8);
String answer = fllm.query(query);
writeResponse(client.getOutputStream(), 200, "OK", answer + "\n");

fllm.query() can throw IOException or InterruptedException. Both are caught by the existing catch (Exception) block in the scaffold, which returns 502. You do not need additional error handling here.

Do not call the fLLM for denied requests. The entire purpose of the gateway is to protect this resource. If the attempt exceeds the limit, you must return 429 and stop. The fLLM should never see a denied request.

Testing

Start the services and the gateway. Test the complete flow:

Basic success

  -H "X-User-ID: alice" \
  -H "Content-Type: text/plain" \

Expected: 200 OK with an ELIZA-style response. Alice is registered with a limit of 10, so the first request should always succeed.

Default caller rate limit

Use an unknown user ID and send four requests. The first three should return 200, and the fourth should return 429: 

for i in 1 2 3 4; do
  echo "--- Request $i ---"
  curl -s -o /dev/null -w "HTTP %{http_code}\n" -X POST \
    -H "X-User-ID: test-$RANDOM" \
    -H "Content-Type: text/plain" \

done

The test-$RANDOM user ID uses the shell's process ID to create a fresh user each time you run the script, so previous test runs do not affect the count. You should see: 

--- Request 1 ---
HTTP 200
--- Request 2 ---
HTTP 200
--- Request 3 ---
HTTP 200
--- Request 4 ---
HTTP 429

Window boundaries: the 60-second window is based on the Time service's clock. If you run this test right at a minute boundary, the window might roll over mid-test and the counter resets. If you see 200 where you expected 429, wait a few seconds and try again with a fresh user ID.

Concurrency testing

The hardest requirement is that the rate limit holds under concurrent load. If three default-tier requests arrive at the same time, exactly three should be allowed — not four or five.

This test sends 6 concurrent requests for the same default user and checks that exactly 3 receive 200 and exactly 3 receive 429: 

USER="burst-$$"
for i in $(seq 1 6); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST \
    -H "X-User-ID: $USER" \
    -H "Content-Type: text/plain" \
    --data "Hello" \
    http://127.0.0.1:8080/chat &
done
wait

The & runs each curl in the background. wait blocks until all of them finish. You should see three 200 lines and three 429 lines, in some order. The order does not matter — concurrency means you cannot predict which specific requests arrive first. But the count must be exactly right.

Why this works: Redis INCR is atomic. Each of the 6 concurrent requests gets a unique attempt number (1 through 6). The requests with attempt numbers 1, 2, 3 are allowed. The requests with 4, 5, 6 are denied. No local counter or synchronization in your gateway code is needed — the correctness comes from using a single atomic operation on the Redis server.

AI assist: if concurrency is not working correctly, try:

"In my Java gateway, I submit two Callable tasks to an ExecutorService using submit(), then call get() on both futures. But the tasks seem to run sequentially. What are common reasons for this, and how can I verify they actually overlap?"

If your WHOIS and Redis calls are sequential, the gateway still produces correct results, but you are not meeting the concurrency requirement. Adding a log line with a timestamp at the start and end of each backend call can help you see whether they overlap.

Completion

If all the tests above pass, review the completion checklist in Section 15 of the project spec. The checklist has 14 items. Walk through each one and confirm your gateway satisfies it. The important ones that are easy to miss:

  • CRLF everywhere. Both request parsing and response writing must use \r\n. A bare \n in your response headers will break compliant clients.
  • Content-Length is byte length. Not character length. If your writeResponse uses body.length() instead of the UTF-8 byte array length, it is wrong for any non-ASCII body.
  • Sockets close on all paths. Backend sockets should use try-with-resources. The client socket is closed in the finally block that the scaffold provides.
  • WHOIS and Redis are concurrent. Both futures must be submitted before either .get() is called.
  • Denied requests do not call the fLLM. Return 429 immediately.
  • Invalid requests do not call any backend. If readRequest() throws, the scaffold catches it and returns 400. No Time, WHOIS, Redis, or fLLM call happens.

Final checkpoint: run the complete test sequence: a valid request, a malformed request, a 404, a 405, the rate-limit sequence (3 allowed then denied), and the 6-request concurrency burst. If all of those work, you are done.

The gateway is a small program, but it exercises the full range of skills this module is about: raw byte-stream framing, multiple wire protocols, concurrent network I/O, and a correct decision under load. Every method you wrote has a clear role in that chain. If something breaks later, you know exactly which piece to investigate because you built and tested each one independently.
