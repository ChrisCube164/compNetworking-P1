HTTP In and Out

Parse requests, write responses, and handle the gateway's outer protocol.

Where you are

In Part 1 you built standalone clients for Time, WHOIS, and Redis. You know how to open a TCP connection, send bytes, read a response with a specific framing rule, and close the socket. Now you are working on the other side: the gateway is a server that receives HTTP requests and sends HTTP responses.

This part covers three methods in Gateway.java:

  1. writeResponse() — the five-argument overload that frames an HTTP response
  2. readLine() — reads one CRLF-terminated line from a byte stream
  3. readRequest() — composes readLine() into a complete HTTP request parser

We start with the response because it is simpler and lets you test immediately. Once you can send a response, you build the line reader, then the request parser. By the end of this part, your gateway will accept a curl request and send back a well-formed HTTP response — even though it does not talk to any backend yet.

Writing HTTP responses

Every HTTP response the gateway sends has this structure:

Gateway → Client 
HTTP/1.1 200 OK\r\n
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 12\r\n
Connection: close\r\n
\r\n
Hello there

The parts:

  • Status line: the HTTP version, a numeric status code, and a reason phrase.
  • Headers: each on its own line, ending in CRLF. The gateway always sends Content-Type, Content-Length, and Connection: close. Some responses add extra headers (like Allow: POST for a 405).
  • Blank line: a CRLF by itself signals the end of the header section.
  • Body: exactly the number of bytes declared by Content-Length.

Every line in the header section ends with \r\n, not just \n. This is a protocol requirement, not a style choice. A client that expects CRLF will break if you send bare line feeds.

Bytes vs. characters

Content-Length counts bytes, not characters. For ASCII text, they are the same. But the gateway sends UTF-8, and some characters take more than one byte in UTF-8. The string "café" has 4 characters but 5 UTF-8 bytes (the é is two bytes).

The correct approach:

  1. Encode the body string to a byte[] using UTF-8.
  2. Use that byte array's .length as the Content-Length value.
  3. Write that same byte array as the body.

Do not use String.length() for Content-Length. Do not encode the body twice (once to measure, once to write). Encode once, measure the array, write the array. 

byte[] bodyBytes = body.getBytes(StandardCharsets.UTF_8);
// Content-Length is bodyBytes.length, not body.length()

Implementing writeResponse

Look at the method signature in Gateway.java: 

private static void writeResponse(OutputStream output, int status, String reason,
                                   String body, Map<String, String> extraHeaders)
    throws IOException

Your implementation needs to:

  1. Encode body as a UTF-8 byte array.
  2. Build the status line: HTTP/1.1 <status> <reason>\r\n
  3. Build the three required headers: Content-Type, Content-Length (using the byte array length), and Connection: close.
  4. Append every entry from extraHeaders as Name: Value\r\n.
  5. Append the blank line (\r\n) that ends the header section.
  6. Write the complete header block as ASCII bytes, then write the UTF-8 body bytes.
  7. Flush the output stream.

The headers are ASCII (status codes, header names, and the Content-Length number are all ASCII). The body is UTF-8. Build the header block as a String, convert to ASCII bytes, and write them. Then write the body bytes you already encoded. Then flush.

Checkpoint: to test before readRequest works, temporarily replace the throw in serve() with a hardcoded response: 

// Temporary test — remove after checkpoint
writeResponse(client.getOutputStream(), 200, "OK", "Gateway is alive\n");

Start the services, run java Gateway.java, and in another terminal: 

curl -i http://127.0.0.1:8080/anything

You should see a complete HTTP response with status 200, correct headers, and the body text. Check that Content-Length says 18 (17 characters plus the newline), not some other number. If it does, your byte-length logic is correct.

Hint: building the header block 
StringBuilder header = new StringBuilder();
header.append("HTTP/1.1 ").append(status).append(" ").append(reason).append("\r\n");
header.append("Content-Type: text/plain; charset=utf-8\r\n");
header.append("Content-Length: ").append(bodyBytes.length).append("\r\n");
header.append("Connection: close\r\n");
for (var entry : extraHeaders.entrySet()) {
    header.append(entry.getKey()).append(": ").append(entry.getValue()).append("\r\n");
}
header.append("\r\n"); // blank line ends the header section

Reading lines from a byte stream

HTTP headers are lines of text ending in CRLF. To parse a request, you need a method that reads one line at a time from a raw InputStream. This is readLine() — and if you built the WHOIS or Redis client in Part 1, you have already written something similar.

The key difference here is the cumulative byte limit. The gateway limits the total size of the request line plus all headers to MAX_HEADER_BYTES (16 KB). The consumed counter is an int[] shared across all readLine() calls for one request, so the limit applies to the entire header section, not to each line separately.

Implementing readLine

The signature: 

private static String readLine(InputStream input, int[] consumed) throws IOException

Requirements:

  • Read byte by byte until you see \r\n.
  • Return the line content without the CRLF.
  • Count both the \r and \n in consumed[0], along with every content byte.
  • If you see a bare \n (without a preceding \r), that is a malformed request — throw a RequestException.
  • If EOF arrives before a complete line, that is also malformed.
  • If consumed[0] exceeds MAX_HEADER_BYTES, throw a RequestException.

The pattern is the same one you used in Part 1: read one byte, check for \r, expect \n to follow, accumulate non-CRLF bytes in a ByteArrayOutputStream. The new parts are the shared counter and the bare-LF check.

Why byte-at-a-time? You cannot use BufferedReader.readLine() here. It consumes bytes from the stream unpredictably — it may read past the header section into the body, which you need to read separately by exact byte count. Byte-at-a-time reading with a raw InputStream gives you precise control over how many bytes are consumed.

Hint: structure 
var line = new ByteArrayOutputStream();
while (true) {
    int b = input.read();
    if (b == -1) {
        throw new RequestException("Unexpected end of request");
    }
    consumed[0]++;
    if (consumed[0] > MAX_HEADER_BYTES) {
        throw new RequestException("Request header section too large");
    }
    if (b == '\r') {
        int next = input.read();
        if (next != '\n') {
            throw new RequestException("CR not followed by LF");
        }
        consumed[0]++;
        // don't need to re-check limit for this one byte
        return line.toString(StandardCharsets.US_ASCII);
    }
    if (b == '\n') {
        throw new RequestException("Bare LF in request header");
    }
    line.write(b);
}

Parsing HTTP requests

With readLine() working, you can now build readRequest(), which reads a complete HTTP request and returns an IncomingRequest record containing the method, path, headers, and body.

An HTTP/1.1 request has three sections, read in order:

Client → Gateway 
POST /chat HTTP/1.1\r\n                    ← request line
X-User-ID: alice\r\n                       ← headers
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 18\r\n
\r\n                                        ← blank line (end of headers)
How are you today?                          ← body (exactly 18 bytes)

The request line

The first line contains three space-separated parts: 

POST /chat HTTP/1.1

Split it on spaces. You should get exactly three parts. Validate:

  • The third part must be exactly HTTP/1.1. Any other version (or missing version) is a RequestException.
  • The first part is the method and the second is the path. Store both. Do not validate them here — serve() handles routing (404 for wrong path, 405 for wrong method) after parsing succeeds.

Parse first, route later. A common mistake is checking for POST and /chat inside readRequest(). The parser's job is to extract a well-formed request. Whether the method and path are supported is a routing decision that belongs in serve(). If you reject GET /chat in the parser, you cannot return the correct 405 status with an Allow header — that logic needs the parsed method and path.

Headers

After the request line, read headers one line at a time until you get an empty line (which signals the end of the header section). Each header line looks like: 

Header-Name: header value

For each header line:

  1. Find the first colon. If there is no colon, the line is malformed.
  2. The name is everything before the colon. The value is everything after. Strip leading and trailing whitespace from both.
  3. If the name is empty after trimming, the line is malformed.
  4. Convert the name to lowercase. HTTP header names are case-insensitive: Content-Length, content-length, and CONTENT-LENGTH are all the same header.
  5. If you have already stored a header with this lowercase name, the request has a duplicate header — reject it.
  6. Store the lowercase name and trimmed value in a Map.

After the header loop, validate the three required headers:

Header (lowercase)Validation
x-user-id Must be present. Value must match [A-Za-z0-9._-]{1,64}.
content-type Must be present. The media type (before any ; parameter) must equal text/plain case-insensitively. So text/plain; charset=utf-8 is valid.
content-length Must be present. Must parse as a non-negative integer. Must not exceed MAX_QUERY_BYTES.

Any validation failure is a RequestException with a descriptive message. The gateway's existing error handling will turn it into a 400 response.

AI assist: if the Content-Type media type extraction is unclear, try:

"How do I extract just the media type from an HTTP Content-Type header value that might include parameters like charset? For example, given 'text/plain; charset=utf-8', I need to compare just 'text/plain' case-insensitively."

The body

After validation, use the Content-Length value to read exactly that many bytes from the input stream. This is the same problem you solved in the Time client: TCP may deliver the bytes in multiple chunks, so use readNBytes() or a read loop. 

int length = Integer.parseInt(headers.get("content-length"));
byte[] bodyBytes = input.readNBytes(length);
if (bodyBytes.length < length) {
    throw new RequestException("Request body is incomplete");
}

After reading the bytes, decode them as UTF-8 to get the query string. If the resulting string is blank (empty or only whitespace), that is invalid — the gateway requires a non-empty query. 

String body = new String(bodyBytes, StandardCharsets.UTF_8);
if (body.isBlank()) {
    throw new RequestException("Query is blank");
}

Finally, return an IncomingRequest with the method, path, an unmodifiable copy of the headers map, and the raw body bytes: 

return new IncomingRequest(method, path, Map.copyOf(headers), bodyBytes);

Why return body as bytes? The IncomingRequest record stores byte[] body, not String body. You already validated and decoded it to check for blankness, but the record keeps the raw bytes. This is a design choice in the scaffold — it preserves the original encoding for downstream use. You can always decode again with new String(request.body(), StandardCharsets.UTF_8) when you need the text.

Putting readRequest together

The complete flow inside readRequest():

  1. Create the shared counter: int[] consumed = {0};
  2. Read the request line with readLine(input, consumed).
  3. Split the request line on spaces. Validate that there are exactly three parts and the version is HTTP/1.1.
  4. Loop: read a line. If empty, the header section is over. Otherwise, parse and store the header.
  5. Validate required headers.
  6. Read the body.
  7. Return the IncomingRequest.

This method will be around 40–60 lines. That is fine. It is doing real parsing work and each line has a purpose. Do not try to compress it into something clever. Straightforward, sequential validation code is easier to debug.

Hint: the header loop 
Map<String, String> headers = new HashMap<>();
while (true) {
    String line = readLine(input, consumed);
    if (line.isEmpty()) {
        break; // blank line ends the header section
    }
    int colon = line.indexOf(':');
    if (colon < 0) {
        throw new RequestException("Malformed header line");
    }
    String name = line.substring(0, colon).trim().toLowerCase(Locale.ROOT);
    String value = line.substring(colon + 1).trim();
    if (name.isEmpty()) {
        throw new RequestException("Empty header name");
    }
    if (headers.containsKey(name)) {
        throw new RequestException("Duplicate header: " + name);
    }
    headers.put(name, value);
}
Hint: validating X-User-ID format 
String userId = headers.get("x-user-id");
if (userId == null) {
    throw new RequestException("Missing X-User-ID header");
}
if (!userId.matches("[A-Za-z0-9._-]{1,64}")) {
    throw new RequestException("Invalid X-User-ID format");
}
Hint: validating Content-Type 
String contentType = headers.get("content-type");
if (contentType == null) {
    throw new RequestException("Missing Content-Type header");
}
// Extract media type (everything before the first semicolon)
String mediaType = contentType.split(";")[0].trim();
if (!mediaType.equalsIgnoreCase("text/plain")) {
    throw new RequestException("Content-Type must be text/plain");
}

Testing with curl

With writeResponse, readLine, and readRequest working, you can temporarily modify serve() to parse the request and echo back what it found. Replace the throw with: 

// Temporary test — remove when you start Part 3
String query = new String(request.body(), StandardCharsets.UTF_8);
String userId = request.headers().get("x-user-id");
String reply = "Parsed OK\nUser: " + userId + "\nQuery: " + query + "\n";

if (!request.path().equals("/chat")) {
    writeResponse(client.getOutputStream(), 404, "Not Found", "Not found.\n");
    return;
}
if (!request.method().equals("POST")) {
    writeResponse(client.getOutputStream(), 405, "Method Not Allowed",
        "Use POST for /chat.\n", Map.of("Allow", "POST"));
    return;
}
writeResponse(client.getOutputStream(), 200, "OK", reply);

Now test each case:

Valid request

curl -i -X POST \
  -H "X-User-ID: alice" \
  -H "Content-Type: text/plain" \
  --data "Hello" \
  http://127.0.0.1:8080/chat

Expected: 200 with parsed user and query.

Wrong path

curl -i -X POST \
  -H "X-User-ID: alice" \
  -H "Content-Type: text/plain" \
  --data "Hello" \
  http://127.0.0.1:8080/wrong

Expected: 404 Not Found.

Wrong method

curl -i -X GET \
  -H "X-User-ID: alice" \
  -H "Content-Type: text/plain" \
  -H "Content-Length: 0" \
  http://127.0.0.1:8080/chat

Expected: 405 with Allow: POST header.

Missing header

curl -i -X POST \
  -H "Content-Type: text/plain" \
  --data "Hello" \
  http://127.0.0.1:8080/chat

Expected: 400 Bad Request (missing X-User-ID).

Wrong content type

curl -i -X POST \
  -H "X-User-ID: alice" \
  -H "Content-Type: application/json" \
  --data '{"msg":"hi"}' \
  http://127.0.0.1:8080/chat

Expected: 400 Bad Request (Content-Type is not text/plain).

Checkpoint: all five curl tests above should return the expected status codes. Check the response headers — Content-Length should match the actual body size, Connection: close should be present, and the 405 should include Allow: POST. If any of these are wrong, fix them before moving on. The HTTP framing must be correct or nothing in Part 3 will work reliably.

What you've built

Your gateway now handles the complete HTTP layer:

  • writeResponse frames a valid HTTP/1.1 response with correct byte-counted Content-Length, CRLF line endings, optional extra headers, and UTF-8 body encoding.
  • readLine reads one CRLF-terminated line from a byte stream, rejects bare LF, tracks cumulative consumption, and enforces the header size limit.
  • readRequest composes line reads into a complete HTTP parser: request line, case-insensitive header map, required header validation, and exact body read by Content-Length.

Combined with the three standalone clients from Part 1, you have all the individual pieces. Part 3 moves them into the gateway and wires them together.
