Why start here

The gateway project asks you to parse HTTP, talk to three backend services, and orchestrate the results concurrently. That is a lot to debug at once. If your WHOIS client has a framing bug, you will not discover it by staring at a 502 response from the gateway.

This tutorial has you build three tiny standalone programs — one per backend service — before you open Gateway.java at all. Each program connects to a running service, sends a request (or not), reads the response, and prints what it got. When all three work, you will have already written most of the backend client code the gateway needs. Transplanting it will be straightforward.

The three services use three different wire protocols. That is the point. Every networked service defines its own rules for what bytes to send and what bytes to expect back. Learning to read those rules and implement them precisely is the core skill this project teaches.

Starting the services

All three backend services (plus the fLLM) start with one command. Open a terminal, cd into your project directory, and run: 

./start.sh

You should see four lines confirming the services are ready: 

TIME_READY tcp=21037 udp=21037
WHOIS_READY tcp=21043
REDIS_RESP_READY tcp=21379
FLLM_READY http=21904

Leave this terminal running. Open a second terminal for your client programs. Every client you build in this tutorial will connect to 127.0.0.1 on one of these ports.

If start.sh fails: make sure you have Java 21 or newer. Check with java -version. The services use single-source execution (java SomeFile.java), which requires at least Java 11, and the gateway itself requires Java 21 for virtual threads.

Service 1: RFC 868 Time

This is the simplest network protocol you will ever see. The client connects. The server immediately sends exactly four bytes and closes the connection. The client sends nothing. There is no request.

Those four bytes are an unsigned 32-bit integer in big-endian (network) byte order. The value is the number of seconds since midnight, January 1, 1900 — not 1970. That is the entire protocol. It is defined in RFC 868, which is shorter than this paragraph.

The wire format

Here is what crosses the TCP connection, in its entirety:

Client → Server 
(nothing — the client sends zero bytes)
Server → Client 
┌────────┬────────┬────────┬────────┐
│ byte 0 │ byte 1 │ byte 2 │ byte 3 │   ← 4 bytes, big-endian unsigned int
└────────┴────────┴────────┴────────┘
(server closes the connection)

"Big-endian" means the most significant byte comes first. Java's ByteBuffer uses big-endian by default, so it matches the wire order without any conversion. But ByteBuffer.getInt() returns a signed Java int, and the protocol value is unsigned. You need to widen it to a long without preserving the sign bit.

Reading the server source

Open services/time/TimeServer.java. It is about 100 lines. The important method is timeMessage() near the bottom: 

private static byte[] timeMessage() {
    long seconds = Instant.now().getEpochSecond() + SECONDS_1900_TO_1970;
    return ByteBuffer.allocate(Integer.BYTES).putInt((int) seconds).array();
}

Read this carefully. It takes the current Unix time (seconds since 1970), adds 2,208,988,800 to shift to the 1900 epoch, casts to int (which keeps only the low 32 bits), and packs it into a 4-byte big-endian array. The cast to int is not a bug — the protocol only has 32 bits to work with.

The TCP handler is serveTcp(): 

private static void serveTcp(Socket client) {
    try (client) {
        client.getOutputStream().write(timeMessage());
    } catch (IOException exception) {
        System.err.println("Time TCP request failed: " + exception.getMessage());
    }
}

The try (client) syntax is called try-with-resources. When the block exits — whether normally or by exception — Java automatically calls client.close(). The server writes four bytes and closes. That is the complete server-side conversation.

Why read the server source? You have the source code for the Time, WHOIS, and Redis services. Use it. When you are confused about what a service expects or returns, the server code is the definitive answer. This is a luxury you will not always have in practice, so take advantage of it. (The fLLM is distributed as a JAR — you interact with it through the provided FakeLLMClient class and do not need to read its internals.)

Building TimeClient.java

Create a new file called TimeClient.java anywhere in your project directory. This is a standalone program, not part of the gateway. Here is the complete implementation: 

import java.io.InputStream;
import java.net.Socket;
import java.nio.ByteBuffer;

public class TimeClient {
    public static void main(String[] args) throws Exception {
        try (var socket = new Socket("127.0.0.1", 21037)) {
            socket.setSoTimeout(3000);

            InputStream input = socket.getInputStream();
            byte[] data = input.readNBytes(4);

            if (data.length < 4) {
                System.err.println("Server sent only " + data.length + " bytes");
                return;
            }

            int signed = ByteBuffer.wrap(data).getInt();
            long unsigned = Integer.toUnsignedLong(signed);
            long window = unsigned / 60;

            System.out.println("Raw bytes:       " + data.length);
            System.out.println("Signed int:      " + signed);
            System.out.println("Unsigned long:    " + unsigned);
            System.out.println("Window (÷ 60):   " + window);
        }
    }
}

Run it: 

java TimeClient.java

Let's walk through every decision in this code.

The connection

try (var socket = new Socket("127.0.0.1", 21037)) {

new Socket(host, port) opens a TCP connection. This is the "active open" — your client reaches out to a server that is already listening. The try (...) ensures the socket is closed when the block exits. You will use this pattern for every backend client in the project.

The timeout

socket.setSoTimeout(3000);

Without a timeout, read() blocks forever if the server never responds. Three seconds is generous for a local service. The gateway spec requires 3-second timeouts on all backend connections. Get in the habit now.

Reading exactly four bytes

byte[] data = input.readNBytes(4);

readNBytes(n) keeps reading until it has n bytes or hits EOF. This matters because TCP is a byte stream — a single read() call might return 1, 2, 3, or 4 bytes depending on how the OS delivered them. readNBytes handles the loop for you. If the server closes early, you get fewer than 4 bytes, which is an error.

Decoding the value

int signed = ByteBuffer.wrap(data).getInt();
long unsigned = Integer.toUnsignedLong(signed);

ByteBuffer.getInt() reads four bytes in big-endian order and returns a Java int. But Java's int is signed, and the protocol value is unsigned. The current RFC 868 value is over 231, so the signed int is negative. Integer.toUnsignedLong() reinterprets those same 32 bits as an unsigned value in a long.

If you skip the unsigned conversion, you get a negative number, a negative window, and a key that does not match what any other correctly-implemented gateway produces. This is the kind of bug that passes a quick test ("I got a number") but fails under real conditions.

Checkpoint: run java TimeClient.java with the services running. You should see a positive unsigned value around 3.9 billion and a window number around 66 million. Run it twice a few seconds apart — the window number should stay the same unless you happen to cross a minute boundary. If the signed int is negative but the unsigned long is positive, the conversion is working.

Why 1900 and not 1970?

RFC 868 was defined in 1983, inheriting the 1900 epoch from earlier NTP-related work. Unix uses 1970. The difference is exactly 2,208,988,800 seconds. You do not need this constant in your client because the gateway only uses the window number (seconds ÷ 60), not a human-readable date. But if you want to verify your value, you can subtract that constant and compare to System.currentTimeMillis() / 1000.

What if I want to test error handling?

Stop the Time service (kill the start.sh process) and run your client again. You should get a ConnectException ("Connection refused"). In the gateway, this will become a 502 response. For now, just notice that the exception happens — you do not need to handle it gracefully in this standalone client.

Service 2: WHOIS

WHOIS is a text-based protocol. The client sends a query, the server sends back a text record, and then the server closes the connection. Unlike Time, the client does send data — one line of text. And unlike Time, the response is variable-length; you read until the server closes its side (EOF).

The real WHOIS protocol (RFC 3912) works exactly this way. The project's WHOIS server is a simplified version that looks up user records instead of domain registrations, but the wire format is the same.

The wire format

Client → Server 
alice\r\n
Server → Client (known user) 
UserID: alice
Tier: REGISTERED
(server closes the connection)
Server → Client (unknown user) 
No such domain: somebody
(server closes the connection)

Key points:

  • The request is the user ID followed by \r\n (CRLF). Not just \n.
  • The response ends when the server closes the connection (EOF). There is no length header and no delimiter marking the end of the record.
  • An unknown user is not an error — it is a successful lookup that returned "not found." The gateway treats this as the DEFAULT tier.
  • The project spec limits the response to 8,192 bytes. Read no more than 8,193 — if you get that many, the response is too large and should be treated as a failure.

What to look for in the server source

Open services/whois/WhoisServer.java and read the serve() method. Notice:

  • It reads one CRLF-terminated line as the query.
  • It looks for a file in registry/ whose base name matches the query.
  • If found, it copies the file contents to the output stream. If not, it writes No such domain: ....
  • Either way, the connection closes when serve() exits.

Also look at the registry/ directory. You will find files like alice.txt. Open one. The records are short — a couple of lines with UserID: and Tier: fields.

Building WhoisClient.java

Your goal: write a standalone WhoisClient.java that connects to the WHOIS service on port 21043, sends a user ID, reads the complete response, and prints both the raw text and the extracted tier.

This time, I am giving you the structure but not the complete code. You know enough from the Time client to handle the connection, timeout, and try-with-resources. The new challenges are:

  1. Sending a request. Get the socket's output stream and write the user ID as ASCII bytes followed by \r\n. Flush the stream so the bytes leave your process immediately.
  2. Reading until EOF. The response has no declared length. You need to keep reading until read() returns -1. A ByteArrayOutputStream is a convenient accumulator — write each chunk to it, then convert to a string at the end.
  3. Extracting the tier. Split the response into lines. Find one that starts with Tier: (case-insensitively). The value after the colon is the tier.

Test it with at least three cases:

User IDExpected result
aliceTier: REGISTERED
nobody"No such domain" → DEFAULT tier
registered-testCheck the registry file yourself

AI assist: if you are stuck on reading until EOF in Java, try asking your AI assistant:

"In Java, how do I read all bytes from a TCP socket's InputStream until the server closes the connection? I need to accumulate the result into a String. Show me using a byte array buffer and a ByteArrayOutputStream."

A specific, technical question like this gets you a useful code pattern. A vague question like "how do I do WHOIS in Java" will get you a library recommendation that does not help you learn the protocol.

Checkpoint: your WhoisClient should print the full response text and the extracted tier for each test case. For alice, you should see REGISTERED. For nobody, you should see the "No such domain" message and your code should treat it as DEFAULT.

Hint: sending the request 
OutputStream out = socket.getOutputStream();
out.write("alice\r\n".getBytes(java.nio.charset.StandardCharsets.US_ASCII));
out.flush();

Use ASCII, not UTF-8. The WHOIS protocol is ASCII. The difference rarely matters for simple user IDs, but being precise about character encoding is a habit that prevents bugs in Part 2 when you handle HTTP bodies.

Hint: reading until EOF with a size limit 
ByteArrayOutputStream buffer = new ByteArrayOutputStream();
byte[] chunk = new byte[1024];
int bytesRead;
while ((bytesRead = input.read(chunk)) != -1) {
    buffer.write(chunk, 0, bytesRead);
    if (buffer.size() > 8192) {
        throw new IOException("WHOIS response too large");
    }
}
String response = buffer.toString(StandardCharsets.US_ASCII);

The read(chunk) call fills up to 1024 bytes and returns how many it actually got. When the server closes the connection, it returns -1. Check the accumulated size on each iteration so you do not read an unbounded response into memory.

Service 3: Redis RESP2

Redis uses a binary-safe protocol called RESP (REdis Serialization Protocol). Unlike Time (fixed length, no request) and WHOIS (text lines, EOF-framed), RESP uses type prefixes and explicit byte counts to frame every message. This makes it more precise but also more demanding to implement correctly.

The gateway only needs one Redis command: INCR. It atomically increments a counter and returns the new value. Your standalone client will do the same thing.

The RESP2 wire format

Every RESP message is a sequence of lines ending in \r\n. The first character of each line identifies the data type:

PrefixTypeExample
+Simple string+OK\r\n
-Error-ERR unknown command\r\n
:Integer:42\r\n
$Bulk string$5\r\nhello\r\n
*Array*2\r\n... (followed by 2 elements)

Commands are sent as arrays of bulk strings. Here is the INCR mykey command on the wire:

Client → Server: INCR mykey 
*2\r\n          ← array of 2 elements
$4\r\n          ← bulk string, 4 bytes long
INCR\r\n        ← the command name
$5\r\n          ← bulk string, 5 bytes long
mykey\r\n       ← the key
Server → Client 
:1\r\n           ← integer reply: the new value after increment

The critical detail is that the number after $ is the byte length of the string that follows, not the number of characters. For ASCII keys (which is all the gateway uses), byte length and character count are the same. But the protocol defines it as bytes.

For your gateway key usage:66000123:alice, the bulk string length would be 22 (the number of ASCII bytes in that string).

What to look for in the server source

Open services/redis-resp/RedisRespServer.java. This one is longer than the other servers, but focus on:

  • readCommand() — how the server parses an incoming RESP array of bulk strings. Notice the * prefix, then repeated $ length-prefixed values.
  • increment() — the INCR handler. It uses ConcurrentHashMap.compute() to atomically read, increment, and store the value. The response is written with writeInteger(), which produces :N\r\n.
  • writeInteger() and writeBulkString() — these show you exactly how the server formats its replies.

Reading the server's parser is particularly useful here. You are building the other side of the same conversation. The bytes your client sends must be exactly what readCommand() expects to receive.

Building RedisClient.java

Your goal: write a standalone RedisClient.java that connects to the Redis service on port 21379, sends an INCR command for a key you choose, reads the integer reply, and prints the result. Run it several times and watch the counter increase.

You are on your own for the structure this time. Here is what you need to figure out:

  1. Construct the RESP command. Build the *2\r\n$4\r\nINCR\r\n$<len>\r\n<key>\r\n byte sequence. String concatenation works fine. Calculate the key's byte length with key.getBytes(StandardCharsets.US_ASCII).length (or just key.length() since the key is ASCII).
  2. Send it. Write the bytes to the output stream and flush.
  3. Read the reply. Read one CRLF-terminated line. The gateway scaffold provides readBackendLine() for this — but since this is a standalone program, write your own or adapt the pattern from your WHOIS client. The reply will look like :1 (after stripping the CRLF).
  4. Parse the integer. Verify the first character is :. Parse everything after it as a long.

AI assist: if the RESP2 encoding is confusing, try:

"Explain the RESP2 wire format for sending a Redis INCR command. Show me the exact bytes that cross the TCP connection, including the array header, bulk string length prefixes, and CRLF terminators. Use the key 'usage:100:alice' as an example."

This kind of question — asking the AI to show you the bytes, not write your code — teaches you the protocol. You can then write the code yourself and know whether it is correct.

Checkpoint: run your RedisClient three times with the same key. You should see the values 1, 2, 3 printed. If you restart the Redis service (start.sh), the counter resets — the data is in-memory only. Try a different key and confirm it starts at 1 independently.

Hint: building the RESP command as a string 
String key = "test:mykey";
String command = "*2\r\n"
    + "$4\r\n"
    + "INCR\r\n"
    + "$" + key.length() + "\r\n"
    + key + "\r\n";

This works because the key is ASCII, so key.length() equals the byte length. Convert to bytes with command.getBytes(StandardCharsets.US_ASCII) before writing.

Hint: reading a CRLF-terminated line

You need to read byte by byte until you see \r followed by \n. Accumulate the non-CRLF bytes. This is the same pattern the Redis server uses in its own readLine() method. Look at it.

Debugging: what if I get an error reply?

If the reply starts with - instead of :, the server is telling you something is wrong. Print the full line. Common causes:

  • Missing or wrong *2\r\n array header
  • Wrong byte count in a $ length prefix
  • Missing \r\n after the key
  • Using \n instead of \r\n

Compare what you are sending against what readCommand() in the server source expects to parse. Byte for byte.

What you've built

You now have three working TCP clients, each using a different wire protocol:

ClientProtocol styleRequestResponse framing
TimeClient Binary, fixed-length None Exactly 4 bytes, then close
WhoisClient Text, EOF-framed One line + CRLF Read until server closes
RedisClient Binary-safe, length-prefixed RESP array of bulk strings Type-prefixed, CRLF-terminated

These three framing patterns — fixed-length, EOF-delimited, and length-prefixed — are the fundamental strategies every application protocol uses to mark message boundaries on a byte stream. HTTP, which you will handle in Part 2, uses a combination of all three: a delimiter-framed header section, a length-declared body, and connection close as a final signal.

More practically, the code you wrote in these clients is close to what you will put into currentWindow(), lookupTier(), and increment() in the gateway. When you get to those methods, you will not be starting from scratch.
